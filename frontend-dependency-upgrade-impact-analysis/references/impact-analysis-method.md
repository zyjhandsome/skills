# 依赖升级影响分析核心方法

## 目录

1. 分析目标
2. 证据顺序
3. 分析与实施时点
4. 影响链路
5. 代码修改点质量
6. 完整性与停止条件

## 1. 分析目标

一份可信的升级分析必须回答：

- 分析对象和真实基线是什么，目标是已知还是待决；
- manifest、lock、peer、engine 和间接依赖如何变化；
- 本机当前激活的 Node 是否满足项目工具链要求，必要时能否隔离执行并可靠恢复；
- 上游在目标区间改变了什么；
- 哪些应用代码直接或间接受影响；
- 哪些页面、路由和业务流程需要回归；
- 风险为什么是这个等级；
- 最低验证、发布控制和回滚触发条件是什么。

## 2. 证据顺序

按以下优先级取证：

| 优先级 | 证据 | 要求 |
|---:|---|---|
| 1 | manifest、lock、peer、engine、overrides/resolutions | 必查；确认声明和真实解析版本 |
| 1 | 本机当前 Node、Node pins、工具链/CI/容器运行时和版本管理器 | 必查；比较本机激活版本与项目命令要求 |
| 2 | 应用侧 import、配置、包装器及调用图 | 必查；落到文件、行号、调用方和业务入口 |
| 3 | 仓库内依赖相关 git diff | 有则检查；区分用户改动、升级改动和生成文件 |
| 4 | 实施后的应用 PR/工作区 diff | 仅用于实施复核；对照预期修改点查漏改和越界 |
| 5 | 上游两版本源码 diff | 默认跳过；仅在大版本、官方资料不足且业务高度相关时按模块定点使用 |

上游事实优先使用官方 migration guide、breaking changes、release、changelog、包元数据和安全公告。任何结论都要能回到来源 URL、仓库路径、符号、测试或命令输出。

## 3. 分析与实施时点

### 升级前

- 当前 lock 的直接解析版本通常应匹配 `from`。
- 未提供 `from` 时，只能从目标 importer 的 lock 直接解析版本或权威 before-lock 推断。
- 未提供 `to` 时进入开放目标处置评估，不把版本缺失当作基线冲突；先评估删除，删除不成立、不确定或未被选择时，再比较同库合规版本和替代库。
- 没有应用 PR diff 属正常状态。
- 报告输出预期修改点、风险和验证计划，不声称已经适配。

### 升级后

- 当前 lock 的直接解析版本通常应匹配 `to`。
- 对照报告检查实施 diff：已覆盖、额外改动、遗漏项。
- 将修改点标成已适配、豁免或后续阶段，不用“构建通过”代替行为验证。

### 基线冲突

如果 claimed `from` 与权威 lock 直接解析版本无法对齐，或者真实直接解析版本无法确定：

1. 展示 claimed from、manifest spec、workspace/importer、lock direct resolution；
2. 标记 `baseline_status=mismatch` 或 `unknown`；
3. 暂停风险批准和实施规划；
4. 等用户或权威 before artifact 确认，不自行选版本。

### Node 运行时冲突

- 项目 pin、`engines.node`、实际工具链或目标包 engines 没有交集时，标记 `constraint-conflict` 并停止。
- 本机当前 Node 不满足项目范围、但存在兼容项目 Node 时，标记 `runtime-switch-required`，生成隔离执行与恢复计划，不修改项目约束。
- 缺少版本管理器或兼容 Node 时只阻塞实施验证；报告一次性安装建议并等待批准，影响分析可继续。
- 实施后必须记录项目命令实际使用的 Node 和原运行时恢复结果。

## 4. 影响链路

至少建立以下链路：

```text
包版本变化
  → 直接 import / 注册 / 配置
  → 公共包装器或基础设施
  → 调用方、组件、页面、路由
  → 业务流程和失败恢复路径
  → 测试、发布观察项和回滚触发条件
```

优先使用代码知识图谱的 symbol search、inbound trace 和 snippet。图不可用时进行有边界的静态搜索，并明确“间接调用关系尚未建立”。不要用零命中证明无使用。

## 5. 代码修改点质量

每一行修改候选必须包含：

| 字段 | 含义 |
|---|---|
| 文件/行号 | 当前代码证据 |
| 类别 | API、组件、请求、样式、构建、类型等 |
| 当前用法 | 简短、可核验的代码或配置 |
| 上游原因 | 具体 release/migration/peer 变化；未知时写待核验 |
| 建议修改 | 可执行但不越过批准边界 |
| 验证 | 能证伪改动是否正确的检查 |
| 优先级 | P0 核心路径/构建阻塞；P1 主要功能；P2 次要或观察项 |
| 可信度 | high=直接证据；medium=规则推断；low=线索 |

静态扫描输出只能称为候选。高可信度修改点必须同时具备应用代码证据和上游依据。

## 6. 完整性与停止条件

### 可交付

- 当前 baseline 已确认；
- exact upgrade 的精确目标已确认，或开放目标模式已按删除、同库合规版本、替代库的顺序呈现证据并保留人工选择；
- lock/workspace 信息明确；
- Node 约束来源、本机当前版本、所选精确项目版本、执行就绪度和恢复方案明确；
- 官方证据覆盖目标区间，或缺口被逐项列出；
- 直接引用、共享包装器和关键调用方已映射；
- 七因素风险分解（含 peer 兼容性）可复算；
- 必测、建议、冒烟、失败和恢复测试已区分；
- 灰度/监控/回滚都有具体触发条件；
- Markdown 通过报告契约校验。

### 必须标为草稿或停止

- baseline mismatch 未决定；
- 权威项目 Node 约束互相冲突，或关键 Node 范围无法解释却声称兼容；
- exact-upgrade 模式的目标版本缺失；
- lockfile 或目标 workspace 无法确定；
- 大版本升级没有 migration/breaking 证据且未标缺口；
- 报告把正则命中直接写成“必须修改”；
- 风险等级没有分值明细；
- 高风险核心流程没有失败/恢复验证。
