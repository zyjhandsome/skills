# GitHub 仓库使用示例文章(房屋风格)

把一个开源仓库写成**可独立阅读、可直接照做**的中文长文。读者从「想快速上手的工程师」到「想快速选型的技术负责人」都能各取所需。

配套文件(全部在本目录,分享时整夹复制即可):

| 文件 | 何时读 |
|---|---|
| [TEMPLATE.md](TEMPLATE.md) | 套骨架时。逐节占位,成稿前删注释 |
| [EXAMPLE.md](EXAMPLE.md) | 写第一篇或卡住风格时。只学节序/六件套/callout/语气,**按目标仓官方资料重写内容** |
| [scripts/validate.py](scripts/validate.py) | 成稿后**必须跑**。机械项不过不交付 |
| [scripts/fix-wikilink-anchors.py](scripts/fix-wikilink-anchors.py) | 存量文里还有 `[[#标题]]` 时 |

`scripts/legacy/` 只修早期「新手专区」污染,新文章不要跑。

> **文章默认互相独立**:不依赖也不引用其它文章。提及姊妹文优先用纯文本「文章名」。绝不用 `[[双链]]`;确需可点击时用 `[文本](<文件名.md>)`。锚点只在文内使用。

## 工作流

按模式选一条,复制清单推进。

### 新写一篇

```
- [ ] 1. 调研:读当前 README / docs / releases,定类型、安装、核心能力、竞品、风险
- [ ] 2. 定主场景:一个可代入的真实任务贯穿全文
- [ ] 3. 建覆盖矩阵:能力全集 × 案例,反查缺口(高频能力必须有案例)
- [ ] 4. 套 [TEMPLATE.md](TEMPLATE.md),每个案例走「六件套」
- [ ] 5. 中文化:行话首次注释;示例输出标「示意」;安装写进案例 A
- [ ] 6. 跑校验: python scripts/validate.py <成稿.md> --type <mcp|cli|skills|rules|flow-cli|lib>
- [ ] 7. 过「人工判断清单」;机械项 + 人工项都过才交付
```

无网或官方页打不开:**停下**,列出缺的来源,不要凭记忆编命令/版本。资料不足的能力在覆盖索引标「未核实」或删案例,不要补假样例。

### 复审 / 按上游更新已有文章

不要整篇重写。对照文末「本文校验」日期抓一次当前 README / release:

1. 命令名、安装脚本、条目清单、分类口径是否变了。
2. 只改漂移处:案例 A 安装命令、覆盖索引、常见坑、校验脚注。
3. 结构已是现行骨架则保持;若仍有「新手专区」或中文序数标题,先改结构再改内容。
4. 再跑 `validate.py --type …`。

## 调研(禁止臆造)

优先用浏览器/抓取读官方一手资料。

取材顺序:README Quickstart / Usage → `examples/` `demo/` → `tests/`(最小可运行调用,最易被忽略) → `docs/` → CHANGELOG / Releases → Issues / Discussions → 包管理页与社区。

无 `examples/`、`tests/` 的仓(纯 SKILL.md / Rules):以 README + 源文件 + 官方分发页 + 社区为准,并在文中注明。

交付前再抓一次当前 README / 分发页,核对命令名、别名、条目增减。拿不准的数字用徽章或「约 / 据官方 / 以来源页为准」。示例输出一律标「**示例 / 示意**」,不得伪装成真实运行结果。

---

## 主场景 + 覆盖矩阵

选**一个**具体场景贯穿始终(例:接手 1200 文件多语言 monorepo:看架构 → 查调用链 → 清死代码 → 合入前看影响面)。避免功能罗列。

1. 列出仓库**全部**功能/命令/子模块(兜底基准)。
2. 做成 `0.3 功能覆盖索引`:功能 | 案例位置 | 第一天需要吗 | 风险。
3. 全集每一行至少对应一个案例;找不到 = 缺口。高频 / README 头号推荐的能力即使不太贴主线,也要给 mini 案例或明确写进索引。

判「典型」须同时满足:功能覆盖无缺口、案例能串成端到端流程、每条用法能追到官方/tests/社区。

### 篇幅与案例数

| 仓库体量 | 建议案例 | 建议成稿 |
|---|---|---|
| 单命令 / 小库 | A + 1～2 个核心案例 | 300–500 行 |
| 典型工具(MCP/CLI/Skills) | A–D 或 A–E | 400–800 行 |
| 能力很多 | 最多到 G,其余进清单/索引 | 不超过 900 行 |

字母 A–G 是上限不是目标。不要为凑 G 而注水。超过 900 行先查重叠(效果表重复、0.1 与整仓原理叠床)。

## 六件套(每个 `## 案例 X` 按此顺序)

旧称「五件套」,以这 6 项为准;缺「你会看到什么」或「效果」即退回重写。

1. **`> 场景`**:此刻处境与痛点。
2. **角色**:读者身份/前置状态。**不得逐字复制场景**。
3. **怎么用**:可复制给 Agent 的那句中文或命令。
4. **你会看到什么(示例输出)**:`text` 块,标题或块内标「示意」。
5. **效果**:本案例特有的「用了 vs 没用」;共性收益只写在「关键收益总结」。
6. **实操卡**:

```text
前置条件: ...
可执行步骤: 1) ... 2) ... 3) ...
验收方式: ...(怎么确认这步成了)
失败处理: 现象 → 解决
风险边界: ...(可逆性/注意)
```

全文只设**一张**「关键收益总结」master 表。各案例效果表只留特有行,并回指该表。

## 文章骨架

正文小节标题**不带中文序数**(不写「一、二、七、」)。顺序靠文档先后 + 案例字母。只有 `0 / 0.1 / 0.2 / 0.3` 保留数字。交叉引用用名称或字母(「见『常见坑』」「见案例 A」),不要写「见第五节」。

| 区块 | 必须? |
|---|:---:|
| 标题 `<工具名> 使用示例:<一句话价值>` | ✅ |
| 开篇电梯简介 | ✅ |
| 自动同步徽章(Stars/release/安装量) | 建议 |
| `## 仓库能力入口一览`:**整仓作用与原理**(含 mermaid)+ 入口/清单 | ✅ |
| `## 0. 案例背景` | ✅ |
| `## 0.1 这个仓库到底是什么?` | 建议;优先回链整仓原理,勿再画第二张架构图 |
| `## 0.2 要不要一上来全量使用?` | ✅ |
| `## 0.3 功能覆盖索引` | ✅ |
| `## 案例 A–…`(A = 安装+首次验收) | ✅ |
| `## 关键收益总结(用了 vs 没用)` | ✅ |
| `## 如何看效果` | 建议 |
| `## 与同类怎么选/怎么叠` | 建议 |
| `## 常见坑` | ✅ |
| `## 实操检查清单` | ✅ |
| `## 底层逻辑`(标题不写死条数) | ✅ |
| `## 参考链接` + 校验脚注 | ✅ |

**架构原理图只放在「整仓作用与原理 → 运行机制」**,用 mermaid `flowchart` 标清哪条边走 LLM、哪些 100% 本地。标签含括号/中文/emoji 时必须加引号:`M["名字<br/>(说明)"]`。`0.1` 不要再画一张重复的图。

整仓原理还须有:一句话电梯、问题→fix→代表命令、典型链路(install → 配置 → 核心流)、竞品边界(若有)。类型专属配置嵌在此节末尾,不单开「新手专区」。

### 案例 A 按仓库类型

| 类型 | 案例 A 必含 | 验收示例 | 禁止(非该类型时) |
|---|---|---|---|
| **MCP Server** | 索引命令、`tools` 数量来源 | Settings → MCP 可见 tools | — |
| **CLI / App** | 终端命令 + `--help` / `list` / `check` | 无报错、产出符合示意 | 「请索引这个项目」 |
| **Skills / 插件** | 安装命令 + `/setup` + 重启宿主 | `/` 或 `@` 能补全 | MCP 索引叙事 |
| **Rules 文件** | 复制路径 + 加载规则 | 新对话行为符合规则 | MCP tools 数量 |
| **流程 CLI** | 流程顺序 + constitution/spec | `.specify/`、`specs/` 存在 | MCP 索引叙事 |
| **库 / 框架** | 包管理器安装 + 最小可运行调用 | 官方 hello-world 能跑 | MCP / Skill 宿主叙事 |

CLI / 流程 CLI 额外给:自检三件套、关键参数速查、多代理对照、Windows 用 PowerShell。库 / 框架覆盖公开主 API 与一个集成场景,不必每个方法一案。

成稿后若目标仓**不是** MCP,全文不得出现 `请索引这个项目`、`Settings → MCP`、`接上 MCP 后先建地图`。

### 徽章与版本(单一来源)

Stars / release / 下载量 / 安装量**禁止手写精确数**。电梯简介后单独一行放 shields.io / skills.sh / npm / PyPI 徽章。正文只写定性(「高活跃 / 头号推荐」)+「定量见徽章」。逐条目安装量改用定性词。

版本号最多硬编码两处:案例 A 安装命令、文末校验脚注。release 徽章已显示 latest 时,正文不必再写同一 tag。

文件名:`<工具名> 使用示例 · <一句话价值主张>.md`。文内锚点用 `[文字](#slug)`,成稿后 `[[#` 必须为 0。

## 机械闸门(脚本判 · 不过不交付)

```text
python scripts/validate.py <成稿.md> --type <mcp|cli|skills|rules|flow-cli|lib>
```

脚本检查:必需区块、无中文序数标题、无「新手专区」、无野生 H1、无 `[[双链]]`、无按序数的交叉引用、文内锚点能跳、每个案例六件套齐全、角色≠场景、实操卡五字段、示例输出标了示意、非 MCP 仓无污染短语、无手写 Stars/安装量、有校验脚注。WARN(徽章缺失、mermaid 未加引号、版本号出现超过 2 处)先修再交。

结构改动后重跑,不要靠全文人工搜索替代。

## 人工判断清单(脚本判不了)

- [ ] 命令/版本/条目已对照**当前**官方页,非记忆
- [ ] 覆盖索引无缺口,高频能力有案例
- [ ] 主场景能串起案例,不是功能说明书
- [ ] 整仓原理图画清 LLM / 本地边界
- [ ] 行话首次出现有中文注释
- [ ] 常见坑覆盖该类型高频卡点(含重启宿主等)
- [ ] 若有竞品,有怎么选/怎么叠
- [ ] 通读无占位符残留、无跨语言乱码

交付前可按文件名 / 逻辑 / 清晰 / 准确 / 时效 / 实用 / 易用 / 重叠 / 可维护 九维自评,低于 8 的维先修。

## 反模式

- ❌ 单独开「新手专区」→ 安装写进案例 A,原理写进整仓作用与原理
- ❌ 只学 EXAMPLE 的仓库内容 / 旧稿序数标题
- ❌ 功能罗列、不绑主场景
- ❌ 只有步骤,没有「你会看到什么 / 效果」
- ❌ 编造命令、工具名、性能数字
- ❌ 示例输出假装真实结果
- ❌ 把 MCP 索引叙事抄到 CLI / Skills / 库
- ❌ 手写 `⭐ Nk+ Stars` 或逐条目安装量
- ❌ `[[双链]]` 互链其它文章
- ❌ 同一组「用了 vs 没用」在每个案例重复
- ❌ 为凑满 A–G 而注水
- ❌ 无网仍凭记忆写安装命令
