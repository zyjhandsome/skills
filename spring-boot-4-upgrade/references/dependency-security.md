# 第三方依赖漏洞检查

Boot BOM 提供经过组合测试的依赖版本，不承诺零漏洞；较新版本也不保证风险更低。目标是识别升级引入或放大的已知风险，并满足组织安全标准，不能保证避免未来披露的漏洞。版本与漏洞结论均须记录核验日期。

## 先建立可比较的基线

1. 使用组织已有的 SCA 工具、漏洞数据源和准入规则；记录工具精确版本、数据库更新时间/快照标识、规则和抑制配置。无既有工具时选适合构建及制品类型的工具，核实覆盖能力，不另造漏洞扫描器。
2. 在原始版本、3.5 检查点、候选 4.x 和最终制品记录实际组件清单与扫描结果。原始基线不要被 3.5 结果覆盖；候选可在隔离副本预解析/扫描，不代表通过 3.5 实施检查点。assess 只生成评估证据，不为接入扫描改业务/构建/部署文件。
3. 同一批比较保持模块、profile、依赖范围、工具、数据库和规则一致。优先同一数据库快照；做不到时尽可能在相近时间重扫源与目标，记录差异及归因限制。不能把数据库新增披露当作升级引入漏洞，也不能用旧基线与新扫描的总数相减证明风险下降。
4. 盘点企业 parent/BOM 中已有安全覆盖、排除、锁文件和扫描约定；更换 parent 或接受 recipe 补丁时逐项复核。目标 BOM 已修复才有依据删除旧覆盖，不能机械照搬，也不能无声丢失修复。
5. 按 [新增与变更依赖发布状态](assessment.md#新增与变更依赖的发布状态) 核验每个实际目标版本，归档 GA/预发布/快照/未知及来源。修复漏洞而再次换版本时重复核验，不能用无漏洞扫描结果替代 GA 证据。

## 扫描实际交付内容

- 依赖图定位实际选中组件和完整引入路径；SBOM 记录组件身份与版本，**生成 SBOM 本身不是漏洞扫描**。记录应用/consumer 模块、profile、快照和制品 SHA256，不能只扫描根 POM 声明。
- 检查最终 jar/war 的嵌套、手工携带和 shaded 组件；部署用镜像时还检查最终镜像 digest 对应的系统包、JDK 和应用层，外置容器/挂载库纳入实际运行范围。依赖图、制品、镜像覆盖互补，镜像构建成功不等于扫描通过。
- runtime/provided、test、构建插件/工具分别记录风险与处置。构建依赖可能接触代码和凭证，不能因不打包就全部忽略；也不能把仅测试依赖描述为已暴露的线上接口风险。
- 对扫描器无法识别的私有、重打包或 shaded jar，列出识别缺口并补维护方 SBOM/公告、源码或人工成分核验。零命中不证明无风险；必需覆盖缺失时保留未验证状态。使用已获授权的数据源，私有 SBOM/源码不默认上传外部服务。

## 比较与处置

按组件身份（优先 purl/完整坐标）、版本及公告关联，归并 CVE/GHSA 等别名，保留原始报告。区分：原有未解决、已修复、引入新受影响组件/版本、配置或可达性变化导致风险上升、数据源新披露、误报/不适用及待确认。总漏洞数下降不能抵消一条新增高风险。

逐项核实官方公告的受影响/修复版本、触发条件、实际调用/配置和依赖路径；严重度需记录来源。不能仅因未搜到调用就判不可达，反射、自动配置和预编译 SDK 可能触发；适用性未知不等于不受影响。

报告逐项列出扫描/公告识别出的 High/Critical（高危/致命）发现，包括原有、新增及拟判误报/不适用项：组件实际版本、公告及别名、严重度来源、受影响条件/适用性证据、维护方修复版本、最终采用版本或其他处置、复扫结果。修复版本未知或尚未发布则如实填写，不能推测；漏洞修复版还须满足发布状态与兼容要求。无此类发现时写明扫描时间、数据库、覆盖范围和识别缺口，不能只输出“安全通过”。

修复顺序按证据选择：

1. 优先评估用户允许目标线内、仍受支持的 Boot 补丁/BOM 组合，以及引入问题的 starter/SDK 兼容版本。目标被精确指定而修复需要变更目标时说明冲突，不静默换版本。
2. BOM 尚未纳入修复时，可在真实 owner 做最小、兼容的版本覆盖，核对同族组件一致性并记录退出条件；重跑解析、二进制兼容、运行和行为验证。不能逐个钉“最新”、单换 Spring 核心 jar、混用 Boot major 或替换私服同一 GAV 的内容。
3. 仅在证明功能不依赖时删除组件或做精准排除；否则评估替代组件、有效缓解或等待维护方修复。无修复版本不等于自动准入，也不为清告警删业务功能。
4. 误报/不适用须有证据；风险接受仅沿用组织已有授权流程，登记准确组件/公告/制品范围、理由、责任人、有效期和复查条件。不扩大 suppression 或降低阈值来制造通过。

兼容桥不是安全豁免。保留 Jackson 2 或其他旧 SDK 时照常扫描；同包名覆盖类不能证明原 jar 漏洞已修复，更不能自动抑制整包告警，须核对具体漏洞路径及最终加载行为。

## 阶段门与交付

- 将 `dependency_security` 作为 migrate 的必需证据项，包含该阶段新增/变更组件的发布状态核验。3.5 阶段要求扫描覆盖、源/中间风险记录及继续迁移的处置依据；这不是发布准入，不要求为修复旧漏洞而升级之前先清零旧漏洞，但组织明确的前置限制仍须遵守。
- 最终阶段要求源/目标差异、最终制品扫描及准入结论。优先组织规则；无规则时默认不得存在未经处置的新增适用 High/Critical 漏洞或已确认的利用风险，适用性待确认的此类发现不能自动通过。已有风险、其他严重度和扫描盲区仍须登记，必要例外须有有效授权；不把“无新增”当成已满足更严格的发布政策。
- 若用户/组织要求最终依赖零 High/Critical，按该规则覆盖原有与新增，不能以“升级未引入”豁免遗留项；误报、不适用及例外是否允许也遵循该规则，不自行降为增量标准。发布状态未核实且无有效例外，同样不得通过两种 verified。
- 分开记录扫描是否成功、覆盖是否完整、策略是否通过。超时、数据库不可用/不符合组织新鲜度要求、必需制品未扫描，均不是零漏洞。扫描退出 0 也可能带有阻断发现，必须读报告与策略结果；两种 verified 状态都不能绕过此门。
- 修改依赖/桥/打包/基础镜像后重建并复扫受影响制品，同时补兼容性回归。交付绑定最终快照、制品哈希、扫描时间及遗留项；发布前按组织时效要求复查，后续持续扫描交给已有 CI/安全流程，不自动创建定时任务。

报告至少保留原始扫描输出、组件清单、发布状态证据、对比结果、覆盖缺口、处置/例外证据及下一步责任人。`check_contract.py` 只检查必需记录、状态、快照及文件哈希，不查询第三方发布状态、不解析漏洞报告或自行判定风险；不能用手填 passed 代替这些工作。

## 工具资料

- [Spring Boot 依赖管理](https://docs.spring.io/spring-boot/gradle-plugin/managing-dependencies.html)：偏离 BOM 需复核兼容性。
- [CycloneDX Maven Plugin](https://cyclonedx.github.io/cyclonedx-maven-plugin/)：生成组件清单；使用实际模块/profile 并核对范围。
- [OWASP Dependency-Check Maven 配置](https://jeremylong.github.io/DependencyCheck/dependency-check-maven/configuration.html)：核实扫描失败、严重度阈值与抑制设置，不能只接受默认退出码。
- [Trivy Java 覆盖](https://trivy.dev/docs/latest/coverage/language/java/)：按输入类型核对 JAR/POM 等识别能力；不能推断所有私有或 shaded 组件均可识别。
