# 批量仓库推进

批量意味着共享方法、版本决策和证据格式，不意味着向全部仓库应用同一文本补丁。没有用户给定仓库清单时，先完成 Skill 或当前仓库任务，不推断邻接路径全部授权迁移。

## 批次清单

可用 [batch-manifest.json](../assets/batch-manifest.json) 作为数据模板。它是记录格式，**不是自动运行 shell 的配置文件**。`null` 表示尚未核实，不等于没有风险。填入真实绝对路径、模块、版本/版本来源、依赖边、状态和报告位置；起始空列表可以直接用于建新批次。

同一批次固定 target minor/patch 和 recipe 版本；合理例外逐仓记录。升级期间有新版本发布时先评估，不在剩余仓库中悄悄改变目标。离线环境可使用组织已有的精确版本与来源快照，但不能声称它们是执行时最新。

## 按依赖与代表性分组

1. 识别公共 BOM/parent、共享 starter/SDK 的 producer-consumer 依赖，先解决阻塞消费者的基础组件。公共模块只提供目标消费兼容性时，不把所有消费者一次性改掉。
2. 按 Boot 起点、Maven/Gradle、Cloud/私有组件、MVC/WebFlux、JPA/消息、WAR/native 分类。先选依赖较少但能代表主要栈的试点；单个简单 MVC 试点不能代表所有 Kafka/native/Cloud 服务。
3. 试点通过后，将确定的 recipe 配置和人工映射用于同类仓库；每仓仍独立解析、dry-run、审查和验证。
4. 高耦合服务、消息共享 schema 或 session 共享场景补做新旧混跑契约。按依赖图确定先后；依赖环需联合方案，不能伪造拓扑顺序。

并行仅用于已有授权、环境容量足够且写集合/外部测试资源独立的任务；不要在同一个工作树让多个执行者同时修改。不自动创建用户侧新任务或推送共享基础组件。

## 状态与断点续跑

逐仓保存 current_stage、status、checkpoints、blocked_by、report 和下一步。状态沿用 SKILL.md 的 assessed / blocked / implemented-unverified / verified-with-bridges / verified；另用 pending、in-progress 表示尚未开始/正在处理。

单仓阻塞只阻塞其依赖的消费者；其他独立仓库继续。涉及公共 BOM 的失败影响范围要回填到批次清单。恢复时复核路径、HEAD、工作区变化、版本 owner 和证据时效，再决定从哪个阶段续跑，避免在旧状态基础上重复转换。

批次完成报告应列出每仓源/目标、状态、验证范围、桥接和责任人/待分配；任何必要仓库仍未验证，不能宣称整批升级成功。这里不承担定时调度、自动发布、自动 PR 或合并；若用户另有授权，按该授权执行。
